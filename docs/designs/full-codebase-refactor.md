## Phase 1 — Server Service Documentation + Typed Errors
**Branch:** `refactor/ck-web/phase-1-server-docs-errors`
**Goal:** Every exported function in every service has a JSDoc. Every controller-facing service has a typed error class.

### 1a. JSDoc Pass — Split-target services only (Phase 1 scope)
JSDoc Phase 1 is scoped to the **6 files being split in Phase 2** (rosterService, ingredientService, complianceService, stockTakeService, prepService, knowledgeManagementService). Adding JSDoc to all 172 service files in a single PR would cause certain merge conflicts with Phase 2 split PRs that touch the same files. The remaining 166 services get JSDoc in a separate follow-on pass (after Phase 2+3 land) — this is tracked in `tasks/todo.md`.

**Quality bar for each JSDoc block:**
- One-line description stating what the function does (not restating its name)
- `@param` for each parameter that isn't obvious from its type (e.g., `organisationId` is obvious; `conflictStrategy: "skip" | "overwrite"` needs a note)
- `@throws {XxxError}` for functions that throw typed domain errors
- No padding; `/** Creates a roster shift. */` is valid if the function is self-evident

**Execution:** Grep each of the 6 split-target services for exported functions (`^export (async )?function` or `^export const.*=`) that don't have a preceding `/**` block. Add one.

### 1b. Typed Error Classes — Controller-Facing Services
Target: services that are directly imported by controllers and currently throw generic `Error`. Math utilities, background workers, and pure utility functions are excluded.

**Controller-facing services that currently lack a typed error class** (verified by grepping service imports in controllers):
Run at execution time: `grep -h "from.*services/" packages/server/src/controllers/*.ts | grep -v ".test." | sort -u` to get the exact list, then cross-reference with the list of services that lack an Error class. The intersection is the target.

**Error class pattern (canonical — match exactly):**
```typescript
export class XxxError extends Error {
  constructor(
    message: string,
    public readonly statusCode: number,
  ) {
    super(message);
    this.name = "XxxError";
  }
}
```

**Per-service checklist:**
- [ ] Add `export class XxxError extends Error { ... }` at top of service file
- [ ] Replace `throw new Error(...)` with `throw new XxxError(..., statusCode)` where the statusCode is semantically correct (404 for not found, 409 for conflict, 403 for access denied, 400 for validation)
- [ ] Update the service's calling controller: ensure the catch block uses `instanceof XxxError` to map `error.statusCode` to the HTTP response. Without this step the typed error is inert. Pattern: `if (err instanceof XxxError) { res.status(err.statusCode).json({ error: err.message }); return; }`
- [ ] Verify the controller's catch block handles `XxxError instanceof` and maps to `error.statusCode`

**Special case — authService:** `authService.ts` has ~20 `throw new Error("UPPERCASE_CODE")` calls (exact count: 24 confirmed by grep). `authController.ts` has 7+ distinct string-match catch sites including `err.message === "EMAIL_EXISTS"`, `"ALREADY_VERIFIED"`, `"INVALID_REFRESH_TOKEN"`, and two `switch(err.message)` blocks covering OAuth codes. Adding `AuthError` without updating ALL 7 catch sites leaves some branches unreachable — they fall through to a generic 500. Tests also currently mock `new Error("CODE")` throws; those mocks must be updated to throw `new AuthError(...)` instances so test breakage gates any incomplete migration. Conversion checklist:
1. Map each string code to its statusCode (e.g. `EMAIL_EXISTS` → 409, `ALREADY_VERIFIED` → 400, `INVALID_CREDENTIALS` → 401)
2. Replace all 24 `throw new Error("CODE")` in authService.ts with `throw new AuthError("human-readable message", statusCode)`
3. Remove all 7+ string-comparison branches in `authController.ts`; replace with `instanceof AuthError` + `err.statusCode`
4. Update all test mocks that throw `new Error("EMAIL_EXISTS")` etc. to throw `new AuthError(...)` instances
5. Run auth integration tests before and after to verify no status code regressions

**E2E sign-off:**
- `pnpm test && pnpm test:integration && pnpm tsc`
- No HTTP status code regressions on tested routes

## Phase 4 — Type Safety Pass
**Branch:** `refactor/ck-web/phase-4-type-safety`

**Context:** `strict: true` is already set in the root `tsconfig.json` and inherited by both packages. The 247 explicit `any` usages are all deliberate casts — they bypass the type checker. This phase eliminates them.

**Baseline:** The `@typescript-eslint/no-explicit-any` rule is currently `"off"` in `eslint.config.js`. Running lint on branch open would return 0 violations (rule disabled) — that count is meaningless. Correct sequence:
1. **First task on this branch:** add `"@typescript-eslint/no-explicit-any": "error"` to `eslint.config.js` (production rules block)
2. Run `pnpm lint 2>&1 | grep "no-explicit-any" | wc -l` — this is the **opening violation count** (expected: ~300+ violations across 95 files)
3. Record the count; phase closes when it reaches zero for production files
4. Test-file occurrences (exempted by the override rule added in the same commit) do not count toward this gate

**Tasks:**
1. **Enumerate all `any` usages:**
   ```
   grep -rn ": any\b\|as any\b\|<any>" packages/ --include="*.ts" --include="*.tsx" | grep -v node_modules | grep -v ".test." | grep -v "dist/"
   ```
2. **Fix each occurrence — decision tree:**
   - `as any` cast to assign to typed variable → find the real type, use `as TargetType` or fix the type mismatch at source
   - `: any` function parameter → use `unknown` + type guard, or a concrete union type
   - `<any>` generic → constrain the generic or provide the concrete type argument
   - Exception: codegen'd files, Drizzle raw SQL placeholders — annotate with `// ponytail: any retained, Drizzle raw query; remove when Drizzle adds typed placeholder support`
3. **Add ESLint rule.** In `eslint.config.js`:
   - Production code: `"@typescript-eslint/no-explicit-any": "error"`
   - Test file override: `{ files: ["**/*.test.ts", "**/*.test.tsx"], rules: { "@typescript-eslint/no-explicit-any": "warn" } }`
   This prevents `any` regressions in production code; test utilities may legitimately use `any` but get a visible warning.
4. **Run tsc + lint** to confirm zero new errors.

**E2E sign-off:**
- `pnpm tsc` passes
- `pnpm lint` passes with new `no-explicit-any` rule
- No runtime behavior changes (type changes must not alter logic)

## Phase 5 — Scheduler Extraction
**Branch:** `refactor/ck-web/phase-5-scheduler`

**Important:** All scheduler helpers (`everyMs`, `onceIfEnabled`, `runNowIfEnabled`, `scheduledJobsEnabled`, and the `Timer` type alias) are currently defined INLINE inside the `app.listen` callback in `index.ts`. They cannot stay in `index.ts` if the cron calls move — they must move to `scheduler.ts` first. These are pure utility definitions that have no dependency on the Express `app` object; moving them is safe.

**Interface decision (decide before writing scheduler.ts):** `scheduledJobsEnabled` reads `ENABLE_SCHEDULED_JOBS` env and has explicit test-race semantics (its comment explains it prevents integration test races on Render). Choose ONE approach and document it in the PR:
- Option A: `scheduler.ts` re-derives `scheduledJobsEnabled` by importing `isProductionProcess` directly (same source, same semantics — safest)
- Option B: `index.ts` passes `enabled: boolean` to `startScheduler({ enabled, log })` (clean interface, testable, preferred if the scheduler ever needs a test)
The `log` (pino) instance should also be passed in or imported — do not reconstruct a second logger instance in scheduler.ts.

**Tasks:**
1. Create `packages/server/src/scheduler.ts` with module-level JSDoc.
2. Move to `scheduler.ts` first (prerequisites for cron calls): `Timer` type, `scheduledJobsEnabled` logic (reads `ENABLE_SCHEDULED_JOBS` env), `everyMs`, `onceIfEnabled`, `runNowIfEnabled`.
3. Move all `setInterval`/`setTimeout`/`runIfClaimed` cron calls from `index.ts` into `export function startScheduler()`:
   - Brain worker tick (BRAIN_WORKER_INTERVAL_MS)
   - Nudges
   - Expiry scan
   - Waste digest
   - Retention purge + prune access log
   - Brain analytics snapshot
   - Brain compaction
   - Brain org digests
   - Capture health check
   - Daily run claims
   - Guest session cleanup
   - Stale document recovery
   - Feedback email processing
4. `index.ts` calls `startScheduler()` after `app.listen(...)` resolves. All scheduler jobs currently run inside the `app.listen` callback — the refactored call goes in the same position (after listen resolves), not after `.then()` chaining.
5. `index.ts` drops from 684 → ~350 lines.
6. Import cleanup: `index.ts` only imports what it actually uses after extraction.

**E2E sign-off:**
- Grep verification: every cron call listed in Task 2 is present in `scheduler.ts` and absent in `index.ts`:
  `grep -c "setInterval\|setTimeout\|runIfClaimed" packages/server/src/index.ts` → 0
  `grep -c "setInterval\|setTimeout\|runIfClaimed" packages/server/src/scheduler.ts` → matches original count in index.ts
- Runtime smoke check: run `pnpm --filter @culinaire/server dev` for 5 seconds; logs must include `"Scheduler started"` (the startScheduler log line) with no startup errors. This verifies the import and init call are wired correctly.
- `pnpm test && pnpm tsc`
