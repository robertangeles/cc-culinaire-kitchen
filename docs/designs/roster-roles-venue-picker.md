## Vision

### Problem

Live-browser QA of the Roster Scheduling Templates feature (`docs/designs/roster-scheduling-templates.md`) found that RC-L4 — "a template row should reject a role belonging to a different venue" — is correctly enforced everywhere the code checks it (client-side filter in `RosterCalendarView.tsx`, server-side `assertLocationInOrg` in `rosterService.ts`), but is unreachable through the product's own UI: the "Add role" form (`RolesManager.tsx`) has no venue field at all, so every role ever created through the UI is permanently org-wide. The parent design doc assumed venue-scoped roles as a precondition without ever specifying how one gets created.

**Terminology:** "venue" and "store location" are the same concept throughout this document — RC-L4 and the UI say "venue," the field and route are `storeLocationId` / `store-locations`.

### 10x Check

A full "Venue × Role" matrix: every role as a row, every venue as a column, toggle cells, with a one-click "copy this venue's roles to bootstrap a new venue" action. Turns roles from a flat list with a hidden per-item property into a real multi-venue staffing planning surface. Not built now — noted as a future direction if the org's venue count grows enough to need it (currently 2 venues, fully overlapping role sets).

## Accepted Scope

- A shared `VenueSelect`-style component (one implementation, not duplicated) rendering "All venues" + each org venue, used by both the Add Role form and the existing-role edit view (`RoleRow`), wired to the existing `create({ roleName, storeLocationId })` / `update(id, { roleName, storeLocationId })`.
- A small venue badge on the collapsed role row when `storeLocationId` is non-null (e.g. "HQ only").
- **The cross-venue-breakage warning is a single-PUT design, not a separate check-then-save round trip**: `PUT /roles/:id` runs the conflict check (a new read against templates using this role at venues other than the target, mirroring `deleteRole`'s existing in-use-template lookup shape) inline, and returns `409` with the conflicting template details unless the request carries `confirmed: true`. The client's Save button, on a `409`, shows the existing app's two-step inline confirm pattern (reused from "Undo Last Generation") with a "Save anyway" action that resubmits the same `PUT` with `confirmed: true`. This was chosen over an original two-call `GET /venue-conflicts` + `PUT` design because the two-call version is a genuine TOCTOU race (another session can create a conflicting template in the gap between the check and the save) — the single-PUT design is atomic, needs no new route, no separate permission decision, and no "disable Save while checking" loading state, all at once. Advisory only — the save still proceeds once confirmed. Live shifts are unaffected since a shift's role is fixed at creation, not re-validated against the role's current venue.
- "Copy roles from an existing venue" action as an **inline field directly inside the existing store-location "create" form**, positioned **right after Classification, before the Address block** (`StoreLocationsSection.tsx`'s `handleCreate`, not a separate always-available action) — usable only at the moment a new venue is created, using an already-existing venue as the copy source. **Hidden entirely when the org has zero existing venues** (the very first venue created for a new org has no copy source). On submit, if a source was picked, the copy batch fires as a follow-up right after the location `POST` succeeds. Fetch the source venue's roles, filter to **only roles whose `storeLocationId` exactly equals the source venue** (excluding the source's own org-wide/null-scoped roles — those are already valid at the new venue with zero action needed; copying them would create a redundant venue-scoped duplicate of something that was never venue-specific), then fire `POST /roster/roles` **directly (not through the `create()` hook wrapper, to avoid its per-call `refresh()`)** once per role against the new venue, **in parallel** (`Promise.allSettled`). **No `refresh()` call afterward** — `StoreLocationsSection.tsx` never displays a roles list itself (that's a different page, `RolesManager.tsx`, which already does its own fresh fetch whenever a user actually navigates there), so there is nothing stale to refresh in this component. If more than one existing venue is available, present a dropdown to pick the copy source; with exactly one existing venue, auto-select it. If the target venue already has a role with the same name, skip it and report it as skipped (not failed). **Non-atomic at the application level** — a mid-batch failure leaves a partial copy; the UI must show which roles copied, which were skipped as duplicates, and which failed, and let the admin retry just the failed subset. **New DB backstop**: a **plain (non-partial) unique index** on `roster_role (organisation_id, store_location_id, role_name)` — Postgres composite unique indexes already treat any row with a NULL column as automatically non-conflicting, so a plain index naturally protects only venue-scoped duplicates while leaving org-wide (null-venue) roles completely unrestricted; no `WHERE` clause needed. **Pre-merge check required**: query dev/prod for existing duplicate `(organisation_id, store_location_id, role_name)` rows before this migration runs — the index creation fails outright if any already exist (possible via the pre-existing raw-API path this whole plan is closing).
- Empty-state text hint (not a clickable action) in the "Manage Templates" modal's role dropdown when zero roles are valid for the current venue — plain text ("No roles exist for this venue yet — add one from the Roles tab"), no cross-tab wiring.

## Outside-Voice Review (CEO stage)

An independent second-pass review (Claude subagent, Codex not installed — same model family, not a true outside model) found the original two-call check+save design was a real TOCTOU race, not just an extra round trip, and that the copy-roles dedup logic had no database backing while parallelizing it actually widened that race. Both findings were accepted and are folded into Accepted Scope above: the single-PUT design replaces the two-call design, and the unique index + raw-POST-plus-single-refresh fix both landed. A third finding — proportionality, whether the warning is worth building now given today's near-zero blast radius (2 venues, fully overlapping roles) — was resolved in favor of shipping it now, since the simplified single-PUT design made it cheap enough that the proportionality objection (raised against the more complex two-call version) no longer applies.

## Engineering Review (implementation-level revisions)

Run via `/plan-eng-review`, 4-section review plus an outside-voice pass. All findings below were presented individually and approved before landing in this doc.

**Architecture:**
- **Reset-on-change (prior-learning match):** this codebase has already shipped and fixed the exact bug class once (`ShiftTimeFields.tsx`'s `confirmed` flag going stale after the underlying field changed again). The venue `<select>`'s `onChange` handler must clear any pending warning/`confirmed` state whenever the value changes, so "Save anyway" can never resubmit against a venue selection the warning wasn't actually computed for.
- **New `RoleVenueConflictError extends RosterError`**, mirroring the existing `AssignmentBlockedError extends RosterError` pattern (`rosterService.ts:58-66`) — carries a `conflicts` payload. `handleServiceError` (`rosterController.ts:124-132`) needs a matching branch, checked **before** the generic `instanceof RosterError` catch-all (the same ordering `AssignmentBlockedError` already requires) — refactored into a small ordered `[ErrorClass, extraField][]` table checked most-derived-first, so this exact "new subclass gets swallowed by the generic branch" mistake becomes structurally impossible rather than merely documented (this is the second time this shape has appeared in this file).
- **`RoleUpdateSchema extends RoleSchema`** (new, update-only) carries `confirmed: z.boolean().optional()` — the shared `RoleSchema` used by the create route stays untouched, so create's accepted body never implies a field it silently ignores.
- **Null-target guard on the conflict check**: widening a role to org-wide (`storeLocationId: null`) can never actually conflict with anything — `generateWeekFromTemplate`'s own existing check already treats a `null` role venue as always-valid (`role.storeLocationId &&` guard, `rosterService.ts:633`). The new conflict-check function must return "no conflicts" immediately when the new `storeLocationId` is `null`, mirroring that exact guard, rather than relying on implicit SQL NULL-comparison behavior to self-resolve correctly.
- **`parseError` (`useRoster.ts:94-99`) is exported and extended** to read `body.conflicts` into `err.conflicts`, mirroring how it already reads `body.blocked` into `err.blocked` for `AssignmentBlockedError` — reused by both `RolesManager.tsx` and `StoreLocationsSection.tsx`'s new raw-POST loop instead of two divergent parsers.

**Regression (mandatory fix, no discussion needed per this repo's Iron Rule):** the existing test `rosterTemplates.integration.test.ts`'s "reports a failed row... when its role's venue was changed via `updateRole`" (line 384-406) deliberately moves a role's venue away from a location a template still references, with no `confirmed` flag — this will now throw the new `RoleVenueConflictError` instead of succeeding. Fix: add `confirmed: true` to that specific `updateRole` call.

**Outside-Voice (eng stage):** re-raised the CEO stage's own proportionality question with a sharper argument — `deleteRole` already hard-blocks the identical relationship ("role used in a saved weekly template") for the sibling delete operation with no override at all, undercutting the earlier "nothing else hard-blocks an edit this way" reasoning. Considered seriously and the warn-and-allow design was kept: an admin editing a role's venue is a normal, expected action (unlike deleting a role outright), and advisory-then-confirm already matches how `generateWeekFromTemplate` treats this exact mismatch elsewhere (visible, not fatal) — hard-blocking would add real workflow friction for a risk this codebase already treats as recoverable everywhere else it appears.

## Design Review (visual & UX revisions)

Run via `/plan-design-review`. 3 visual mockup variants generated and reviewed on a comparison board; Variant C approved (see Approved Mockups below). All findings presented individually and approved before landing here.

- **Warning copy corrected for honesty:** the approved mockup's warning banner text ("This action cannot be undone") is factually wrong for this action — re-scoping a role's venue is trivially reversible by editing it back, unlike the genuinely destructive "Undo Last Generation" flow this UI pattern is borrowed from. Corrected copy: *"Templates at other venues will stop showing this role until you either revert this change or update those templates."*
- **"Save anyway" button color corrected for consistency:** since the copy no longer claims irreversibility, the button uses this app's normal `bg-gold`/`border-gold` accent (matching every other primary action in `RolesManager.tsx`), not the solid red reserved for genuinely destructive, irreversible actions elsewhere in this app (e.g. Undo Last Generation's "Confirm — cancel these shifts").
- **Mockup scope boundary:** the approved mockup depicts a fuller page (sidebar nav, breadcrumb, search bar, a USERS column, per-role icon badges) than what this plan builds. Only the following visual language transfers into the real implementation — the page structure and new icons do not:
  - **Venue badge** (collapsed role row): `inline-flex items-center rounded-full border border-gold/30 bg-gold/10 px-2 py-0.5 text-xs text-gold`, e.g. "HQ only" — `animate-scale-in` on first appearance, matching `RosterTemplatesPanel.tsx`'s existing convention for new elements appearing in this feature area.
  - **`VenueSelect`**: same input chrome as the existing Role name field in this file (`rounded-lg bg-dark-100 border border-dark-200 px-3 py-2 text-sm text-white focus:outline-none focus:border-gold/50`).
  - **Warning banner**: `rounded-lg border border-gold/20 bg-gold/10 px-3 py-2 text-sm text-gold` (caution, not alarm — matches the corrected copy's actual stakes), `role="alert"`, `animate-scale-in` on appearance. "Save anyway" as a `bg-gold hover:bg-gold-hover text-dark` button (this app's standard primary-action treatment); "Cancel" as a plain text button, matching the existing Add Role form's Cancel button.
- **Desktop-only, stated explicitly:** no responsive/mobile treatment exists anywhere in Roster admin or Settings today; this plan doesn't add any either. Stated here so it reads as a deliberate match to existing convention, not an oversight.
- **Copy-roles field position:** goes right after Classification, before the Address block, in the create-location form — grouped with the venue's other structural/setup decisions, not its physical-location details.

- **Full Venue × Role matrix admin view** — 10x vision, correctly out of proportion to the current 2-venue scale.
- **Bulk server-side role-copy endpoint** — the client-loop + DB unique-index combination already closes the correctness gap; a dedicated endpoint only earns its keep if the loop becomes a real support burden.

- **Full cross-tab pre-filled navigation** from the Templates modal empty state to the Roles tab — descoped to a plain text hint; the empty state is rare enough not to justify new tab-switching plumbing through `RosterPage.tsx`.

- `handleAdd`'s `saving`-disabled-button pattern — reused for the new copy-roles and edit-venue save states.

## Dream State Delta

This plan closes the gap between "every role is permanently org-wide" and "any role, new or old, can be scoped or unscoped, with a safety net against breaking existing usage elsewhere" — the middle column of the Dream State diagram above. It deliberately does not build the right-hand column (the full matrix, venue bootstrap search/filter) — those remain correctly deferred until venue count or role divergence actually grows past today's 2-venue, fully-overlapping-roles reality. The new conflict-check query and shared `VenueSelect` component become direct building blocks for that future work.

## Error & Rescue Registry

| Method/Codepath | What Can Go Wrong | Exception Class | Rescued? | Rescue Action | User Sees |
|---|---|---|---|---|---|
| `PUT /roles/:id` (venue change) | Conflicting templates at another venue, `confirmed` not set | `409 Conflict` | Y | Client shows two-step inline warning (reused "Undo Last Generation" pattern) | Warning banner + "Save anyway" |

| `PUT /roles/:id` (venue change) | Role deleted elsewhere mid-edit | `404` | Y (existing) | Inline error | Existing inline error message |
| Copy-roles: one `POST /roles` in the batch | `400`/`401`/network failure | thrown `Error` per settled promise | Y | Collect into failed list, continue batch | "Copied N of M. Failed: [...]. Retry failed" |
