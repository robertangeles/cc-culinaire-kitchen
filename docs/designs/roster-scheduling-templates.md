## Problem Statement

CulinAIre's roster module lets a manager build a schedule by creating shifts one at a time — via a form (Shifts tab) or by dragging on a 7-day calendar grid (Calendar tab). Both are per-shift primitives. Real hospitality rosters are overwhelmingly recurring: the same roles work close to the same hours every week, because venue opening/closing hours are fixed. Recreating that pattern from nothing, one shift at a time, every single week, is exactly the "loses the purpose of having a system" complaint this session investigated.

## Demand Evidence

Two independent, named sources converged on the same complaint:
- **Alex (co-founder)**, testing the product directly, hit the per-day creation friction and flagged it.
- **Chef John Hand, Head Chef of St Georges Restaurant** — an external operator, not a co-founder — raised the same objection unprompted: "if we have to create shifts every day, that loses the purpose of having a system."

Calibration: Alex's signal is a design flaw the team found internally, not market validation. John Hand's is the stronger evidence — an actual operator, independent of the product, converging on the identical complaint without being led to it.

## Status Quo

User's own description, later confirmed against primary competitor documentation (see Cross-Model / Landscape section below): most hospitality venues run a single recurring weekly pattern — Monday through Sunday — built around standard, fixed opening/closing hours. Two populations of staff exist within that pattern: those whose shifts track the venue's advertised open/close hours (front-of-house, service), and those whose shifts fall outside it (prep arriving before open, cleaning staying after close).

## Target User & Narrowest Wedge

Target: the person who actually builds the roster by hand today — confirmed via Chef John Hand (Head Chef, St Georges Restaurant), a specific, named, external operator, not a category. Narrowest wedge: a saved weekly pattern per venue, made up of one row per (role, day-of-week) — a role active on multiple days has multiple rows, and split shifts (e.g. a lunch and dinner service for the same role/day) are multiple rows too, not a single aggregate record. Reusable to generate a new week's Draft shifts in one action — not a full recurring-event engine, not assignee-level automation.

## Constraints

- CulinAIre is pre-product — no real venues live yet, so this is greenfield scope with zero migration or compatibility cost.
- Must reuse the existing Draft-shift pipeline (`createShift`, the Calendar tab's rendering, `roster:manage` permission) rather than introduce a parallel mutation surface.
- No new permission key needed — templates are managed under the existing `roster:manage` gate, same as roles and shifts.

## Premises

1. CulinAIre's per-shift data model and week-grid Calendar view are structurally correct and match industry convention — not what needs to change.
2. The actual friction is the absence of a template/copy-previous-week mechanism, which competitors (7shifts, Deputy) treat as a first-class feature, not an afterthought.
3. Since CulinAIre is pre-product with no real venues on it yet, there's no migration/compatibility cost to adding this now — it's pure greenfield scope, not a retrofit.

All three confirmed by the user without revision.

## Landscape Research (Phase 2.75 — in place of Cross-Model Perspective, which was skipped by user choice)

Directly verified, not assumed:
- **7shifts** ships named "Scheduling Templates": a blueprint (role + time + qualifications, per day-of-week), reusable across weeks and locations, distinct from a live schedule. Recommended practice for the exact BOH/FOH split described above: stagger BOH (prep) earlier, stack FOH closer to service — each role gets its own template time, independent of the venue's stated hours. ([7shifts Scheduling Templates](https://kb.7shifts.com/hc/en-us/articles/4417514429459-Scheduling-Templates))
- **Deputy** ships "Copy from previous week" plus save/load templates, and can bulk-copy a single shift, a day, or a 2-4 week block between date ranges in one action. ([Deputy: Copy shifts](https://help.deputy.com/hc/en-au/articles/4688828103439-Copy-shifts-to-another-date-or-area-on-the-schedule))

**Key finding:** under the hood, both competitors still store a shift as an individual date+time+role+person record — the same primitive CulinAIre already uses. The complaint was never "day-based vs. week-based data model." It's a missing acceleration layer on top of a correct primitive.

## Approaches Considered

**Approach A: "Copy last week"** — one action, bulk-duplicates the prior 7-day window's shifts into the current week. Rejected — corrected reasoning after outside-voice review: the original "bootstrap problem" framing (nothing to copy in week 1) was flawed, since Approach B has the identical cost — someone hand-authors the first full pattern from nothing either way. The real reason to reject A: its output is just this week's data copied forward with no separate, editable source of truth, and a mistake in week 1 silently propagates forward with no named pattern to fix once. B costs the same to bootstrap and produces a durable, reusable artifact instead.

**Approach B: Named Roster Templates (recommended)** — a new entity: role + day-of-week + start/end time + venue, independent of any specific week — a blueprint, not a live shift, matching 7shifts' own framing exactly. A "Generate this week from template" action creates real Draft shifts from it via the existing `createShift` pipeline. Editable and reusable indefinitely; a new venue can set this up once, before ever running a live week.

**Approach C: Recurring shifts (RRULE-lite)** — a "repeat weekly until" option on the Calendar's create-drag itself. Rejected: per-occurrence edit semantics ("this shift vs. all future ones") are a well-known bug-prone surface (DST, partial edits, series divergence) for a payoff Approach B already covers more cleanly.

## Recommended Approach

**B.** CulinAIre is pre-product — this is exactly the moment to build the correct long-term shape (named, declarative, works from day one) rather than a stopgap that has to be replaced once real venues onboard.

## Proposed Entity & Generation Semantics

Full column list and indices below — filled in during `/plan-eng-review` per this repo's own mandatory pre-schema checklist (2NF, FK indexing, naming), which an earlier draft of this doc skipped (caught by outside-voice review):

```
roster_shift_template
  roster_shift_template_id  uuid PK, default random
  organisation_id           integer NOT NULL FK -> organisation      (same pattern as shift/roster_role: org-wide template management views need this directly, not derived through store_location)
  store_location_id         uuid NOT NULL FK -> store_location        (NOT NULL — see "Multi-venue scoping" below, matches shift's mandatory venue scoping, not roster_role's nullable one)
  roster_role_id            uuid NOT NULL FK -> roster_role
  day_of_week               smallint NOT NULL                        (0=Sunday..6=Saturday, same convention as staff_availability.day_of_week)
  start_time                varchar(5) NOT NULL                      ("HH:MM", same convention as staff_availability.available_from/until)
  end_time                  varchar(5) NOT NULL
  created_dttm              timestamptz NOT NULL, default now()
  updated_dttm              timestamptz NOT NULL, default now()

Indices:
  idx_roster_shift_template_org       (organisation_id)              -- FK index, org-wide template list
  idx_roster_shift_template_location  (store_location_id)            -- generation's own lookup: "every row for this venue"
  idx_roster_shift_template_role      (roster_role_id)                -- FK index, feeds deleteRole's new in-use check
```

No separate uniqueness constraint on (role, day, start, end) — the overlap-validation check below already rejects an exact duplicate as a degenerate case of "overlapping," so a second constraint would be redundant.

- **Table name:** `roster_shift_template` (singular). CLAUDE.md's written convention says plural, but every existing table in this schema — including every sibling in this exact domain (`roster_role`, `shift`, `shift_assignment`, `public_holiday`, `shift_swap_request`) — is singular in actual practice. **Flagging explicitly, per outside-voice review, rather than burying this as a parenthetical: this is a deliberate deviation from CLAUDE.md's written rule, made because 100% of existing tables contradict that rule — not an oversight.** Naming this one plural would make it the only exception, not the convention-follower.
- **Cardinality:** one row per (role, day-of-week, start time, end time). Multiple rows per role/day are expected and required — this is how a split shift (lunch + dinner service for the same role) is represented, not a special case.
- **Overnight shifts:** a template row's day-of-week anchors to its **start** day. An end time earlier than the start time on the same row is interpreted as crossing into the next calendar day — the same time-only rollover inference `shiftEndTimeOnStartDate()` (`rosterService.ts`) already performs for live shifts, which is the actual precedent here, not `shift`'s own storage (that table holds full timestamps and never infers rollover from a bare time comparison). Start time equal to end time is rejected at template-save time (zero/full-day duration is ambiguous data entry, not a valid pattern) — matches the same strictly-positive-duration invariant `shift` itself already enforces (`chk_shift_time_order`).
- **Overlap validation at save time (gap found by outside-voice review):** the generation-time conflict check only prevents the SAME template row from double-generating across concurrent calls — it does nothing to stop two DIFFERENT template rows for the same role/day with overlapping times from both being saved, then both generating overlapping shifts in a single generation call (the unique-index guard never fires between two distinct rows). `createTemplate` must reject (400) a new row whose time range overlaps an existing row for the same (role, day-of-week) — same time-overlap comparison already specified for generation, just enforced once more at the source so a manager can never save a self-contradicting template in the first place.
- **Role-venue consistency:** a template row's role must be valid at the template's venue — reject (400) at save time if the role's `storeLocationId` is non-null and differs from the template row's `storeLocationId`, the same check `createShift`'s `assertLocationInOrg` already performs for live shifts.
- **Multi-venue scoping:** `storeLocationId` on the template row is `NOT NULL` — the same mandatory, always-tied-to-one-venue scoping `shift.storeLocationId` uses, not `roster_role`'s optional/nullable "applies at every venue" scoping. Generation always operates on the currently-selected venue, never across venues in one action.
- **Local time → UTC instant (new code, verified by outside-voice review not to exist yet):** `rosterService.ts` currently only has the reverse direction (`toVenueLocalDate`/`toVenueLocalTime`, instant→local). Generation needs a new pure helper — `resolveVenueLocalToUtc(dateIso, hhmm, ianaTimezone): Date` — built on `Intl.DateTimeFormat`'s own offset-resolution for the given IANA zone (same primitive `toVenueLocalDate` already uses, inverted), not a new date library — this repo has zero date-timezone dependencies today and an explicit convention against adding one for what a few lines can do. Since generation always targets a specific, concrete future week (never an ambiguous "any year"), the one genuine edge case worth a test is a target date that falls exactly on a DST transition in the venue's zone.
- **Generation conflict handling:** fetches the venue's existing **Draft or Published** shifts for the target week **once** (a single query, widened slightly past the week's boundary to catch an overnight shift generated near a week edge), then compares each template row against that in-memory set using **time-overlap**, not exact start/end equality — a manager nudging one generated shift's time by 15 minutes and re-running generation must still be detected as a conflict, or "zero duplicates" in the Success Criteria below doesn't actually hold. **Cancelled shifts never count as a conflict** — a cancelled generated shift must be regeneratable, not permanently block that slot. One query per generation call, not one per template row — matches this codebase's own established "batch, don't loop" convention (the same fix already applied to publish-notifications this session). Default: **skip** any slot whose time range overlaps a non-cancelled existing shift, and report the skipped count to the manager — never silently overwrite or duplicate. No separate confirmation step needed since skipping is non-destructive by construction.
- **Venue timezone lookup:** `getVenueTimezone` is called **once** per generation call, before the per-row loop, not once per template row — the venue's timezone is constant across every row being generated in the same call.
- **Holiday/closure interaction:** generation does **not** resolve `isPublicHoliday` at creation time — same as a manually-created shift today (confirmed: `createShift`/`ShiftSchema` never touches the holiday calendar), that flag is left `false` and only (re-)computed by `publishRoster()`'s existing gate at publish time. Templates get no separate holiday-skip rule; this is deliberate consistency with the existing manual-creation path, not an oversight.
- **Role deletion:** `deleteRole` already blocks deletion (409) if any `shift` row references the role, to avoid orphaning live shifts. It needs the identical guard against in-use `roster_shift_template` rows — deleting a role used only in a template today (no shifts scheduled yet) must not throw a raw FK-constraint 500 or silently cascade-delete the manager's saved template. Same 409 pattern, same message shape as the existing `shift` check.
- **Partial-failure semantics:** generation is **best-effort per-row**, not a single transaction — matches `publishRoster()`'s own established pattern in this codebase (process each row independently, one bad row never blocks the others). Returns `{created: N, skipped: N, failed: N}` counts; a failed row (e.g. its role was deleted between listing templates and generating) is reported, not silently dropped or allowed to abort the batch.
- **Concurrent-generation race:** the per-row conflict check is SELECT-then-conditionally-INSERT, not atomic — a double-click or two near-simultaneous generation calls for the same venue/week could both pass the check before either insert commits. Closed the same way `assignStaff`/`claimSwap` close their own decline-reactivation race, but implemented as an **upsert** (`insertOrReactivateAssignment`'s exact idiom), not a bare insert + `23505` catch — a plain catch turned out to be insufficient on its own, see below. Concretely: `shift` gains two new nullable columns, `sourceTemplateRowId` (FK to the template row that generated it, null for manually-created shifts) and `generatedForWeekStart` (the Monday-anchor date of the target week), with a unique index on `(sourceTemplateRowId, generatedForWeekStart)`. The insert uses `.onConflictDoUpdate({target: [sourceTemplateRowId, generatedForWeekStart], setWhere: eq(status, "Cancelled"), ...})`: a genuine double-click race lands on a still-Draft/Published row, matches no row via `setWhere`, and simply returns nothing (no exception, no duplicate) — folded into `skipped`. This also gives free auditability: which shifts came from a template, and for which week. `shift.sourceTemplateRowId` is `ON DELETE SET NULL` (found missing by outside-voice review): since generated shifts are never deleted, only cancelled, a `RESTRICT` FK would make a template permanently undeletable the moment it's ever used once — directly contradicting "reusable indefinitely." `SET NULL` keeps the already-generated shift untouched and lets the template be deleted anytime; the tradeoff is losing the "which template generated this" link for shifts that predate the deletion, which is an honest, minor cost.
- **Rollback:** a mistaken generated shift is **cancelled** the same way any Draft shift is today (there is no delete-shift route — only `POST /shifts/:id/cancel`, which sets `status = 'Cancelled'` and keeps the row). Because the row survives cancellation, it still occupies the unique key above — **caught during implementation, not at design time**: a bare `INSERT` + `23505` catch would have treated that occupied key as a permanent conflict, silently blocking every future regeneration of a cancelled slot, contradicting this exact bullet's own stated intent. The `onConflictDoUpdate` above resolves it in the same mechanism as the concurrency fix: regenerating a cancelled slot's `setWhere` condition matches (`status = 'Cancelled'`), so the existing row is revived in place (fresh role/times, `status` reset to `Draft`) rather than erroring or staying permanently skipped.
- **Bulk undo (in scope, per explicit user decision to build now rather than defer):** `POST /roster/templates/undo-generation` (`storeLocationId`, `weekStart`) cancels every shift matching `sourceTemplateRowId IS NOT NULL AND generatedForWeekStart = weekStart` for that venue — reuses the same two columns already added for the concurrent-generation race fix, no new schema needed. This is scoped to "everything generated for this venue/week," not per-template-row, matching the natural undo scope for a single "Generate this week" action (which itself touches every template row for that venue at once). Returns a cancelled count. Same cancel semantics as cancelling one shift individually — no new state, just a bulk loop over the existing cancel path.
- **Assignee defaults:** role + time only, no default assignee per slot. Baking in a default assignee risks generating shifts against someone whose availability or compliance status has since changed. Assignment stays a manual step after generation, same as it is for a hand-created shift today.
- **Editing a template:** a blueprint, not a live schedule — editing a template only affects future generations, never shifts already generated from an earlier version of it, matching 7shifts' own framing. This needs a real `PATCH /roster/templates/:id` route (found missing by outside-voice review — the original route list only had create/list/delete/generate, with no way to actually edit a row). Delete-then-recreate was considered and rejected: it would sever `sourceTemplateRowId` on that row's already-generated shifts via the `SET NULL` above, for a row whose past generations didn't actually change — a real update route is barely more code and avoids that collision entirely. Same overlap/role-venue validation as `createTemplate` applies on update.

## Generation flow (diagram)

```
POST /roster/templates/generate  (storeLocationId, weekStart)
  │
  ├─ getVenueTimezone(storeLocationId)                    [once, not per-row]
  ├─ fetch venue's Draft/Published shifts for target week  [once, not per-row]
  │   (widened slightly past week boundary for overnight edge cases)
  │
  └─ for each template row (best-effort, independent):
       │
       ├─ role still valid at this venue? ──────── no ──▶ failed++
       │        │ yes
       ├─ resolve (day-of-week, HH:MM) + tz ──▶ UTC startDatetime/endDatetime
       │        │
       ├─ overlaps an existing non-cancelled shift? ── yes ──▶ skipped++
       │        │ no
       └─ INSERT shift (sourceTemplateRowId, generatedForWeekStart)
                │
                ├─ success ──▶ created++
                └─ 23505 (concurrent generation won the race) ──▶ skipped++

  return { created, skipped, failed }

POST /roster/templates/undo-generation  (storeLocationId, weekStart)
  └─ cancel every shift WHERE sourceTemplateRowId IS NOT NULL
                          AND generatedForWeekStart = weekStart
                          AND storeLocationId = storeLocationId
     return { cancelled }
```

## Failure modes

| Codepath | Realistic failure | Tested? | Handled? | User sees |
|---|---|---|---|---|
| `createTemplate` | Two overlapping rows submitted for same role/day | Yes (new test) | Yes — 400 at save time | Clear rejection, not a later silent conflict |
| `generateWeekFromTemplate` | Role's venue changed after template creation | Yes (new test) | Yes — row fails, batch continues | `failed` count includes it; rest of week generates |
| `generateWeekFromTemplate` | Two concurrent generations, same venue/week | Yes (new test) | Yes — `23505` caught, folded into `skipped` | No error; no duplicate shift |
| `generateWeekFromTemplate` | Overnight row near week boundary | Yes (new test) | Yes — widened query catches it | Correctly detected as a conflict, not double-booked |
| `deleteTemplate` | Template already has generated shifts | Yes (new test) | Yes — `SET NULL`, shifts untouched | Template deletes cleanly |
| `deleteRole` | Role referenced by a template, no shifts yet | Yes (new test) | Yes — 409, same shape as existing shift-in-use check | Clear rejection naming the reason |
| `undo-generation` | Run twice for the same venue/week | Yes (new test) | Yes — already-cancelled shifts are no-ops | Second run reports 0 cancelled, no error |

No critical gaps (untested + unhandled + silent) — every new codepath above has both a planned test and a defined behavior.

## UI Placement (from `/plan-design-review`, 2026-09-07)

Resolved: **inline on the existing Calendar tab**, not a new "Templates" sub-tab — the user's explicit choice, overriding the reviewer's recommendation (a new tab, which a codebase survey found mechanically trivial to add: a one-line push into `RosterPage.tsx`'s `tabs` array plus one conditional render, versus touching the Calendar tab's toolbar).

**Concrete design**, to keep the Calendar grid's existing hand-rolled drag-gesture/pointer-events code (already flagged in this codebase as dense and fragile) completely untouched:
- A new second toolbar row in `RosterCalendarView.tsx`, below the existing week-nav/Staff-drawer row: a "Templates" label plus three buttons — **Manage Templates**, **Generate This Week**, **Undo Last Generation**.
- Each button opens a **modal dialog** (centered, dimmed overlay), never a floating popover anchored to the toolbar — a popover overlapping the grid was mocked up and explicitly rejected as visually cramped and code-risky (it would have needed to coexist with the grid's own z-index/pointer-event handling).
- "Manage Templates" modal: a day-of-week-grouped list of template rows (role + time range + edit/delete), reusing the existing `EmptyState` component (`packages/client/src/components/ui/EmptyState.tsx`) for the zero-templates state, plus a "+ Add Template Row" action — matches this codebase's existing dark/gold visual language (`bg-dark`/`border-dark-200`/`text-gold` glow), not the generic "amber" literal CLAUDE.md's example classes name.
- "Generate This Week" modal: a target-week picker + confirm, returning the `{created, skipped, failed}` counts from `generateWeekFromTemplate`.
- "Undo Last Generation" modal: a confirmation step (this cancels real shifts) before calling `POST /roster/templates/undo-generation`.
- Rejected alternative: direct grid editing (defining template rows by interacting with calendar cells in a "template mode") — explicitly rejected by the user because it would extend the fragile drag-gesture code with a second interaction mode, for no material UX gain over a modal.

- **Unit** (`rosterService.test.ts`): start==end rejection; overnight day-anchoring resolution (mirroring `shiftEndTimeOnStartDate`'s existing pure-function pattern); `{created, skipped, failed}` aggregation across mixed-outcome rows.
- **Integration, real-DB** (extend `roster.integration.test.ts` or new `rosterTemplates.integration.test.ts`): `createTemplate` (role-venue mismatch → 400; overlapping row for the same role/day → 400; valid same-day + overnight rows); `updateTemplate` (same overlap/role-venue validation as create); `listTemplates` (venue/org scoping); `deleteTemplate` (cross-org 404; success; **deletes cleanly even after it has generated shifts** — `sourceTemplateRowId` on those shifts goes null, the shifts themselves are untouched); `generateWeekFromTemplate` (no-conflict create; Draft/Published-only conflict skip, Cancelled excluded; **failed row when its role's venue was changed via `updateRole` after the template was created** — corrected via outside-voice review from an original "role was deleted" scenario that `deleteRole`'s own new guard makes unreachable; week-boundary overnight row doesn't double-book the next week; DST-transition target date resolves correctly); **regression-class, mandatory per this repo's own IRON RULE**: `deleteRole`'s new in-use-template guard (409) — this modifies existing, already-tested behavior, so this test is required, not optional; **concurrency test**: two concurrent `generateWeekFromTemplate` calls for the same venue/week — exactly one row is created, the other's `23505` folds into `skipped`, matching the existing pattern already proven for `assignStaff`'s own concurrent-reactivation race in `roster.integration.test.ts`.
- **Permission boundary** (extend `rosterPermissions.test.ts`): all six new template routes (create, list, update, delete, generate, undo-generation) each get the standard 401 (no token) / 403 (wrong permission) / 200 (`roster:manage`) / 200 (Administrator bypass) rows, matching this file's existing table-driven pattern.
- **`undo-generation` integration coverage**: cancels exactly the shifts matching the given venue/week's `sourceTemplateRowId`/`generatedForWeekStart` pair, leaves manually-created shifts and other weeks' generated shifts untouched, and is idempotent (running it twice cancels nothing the second time, since already-Cancelled shifts don't need re-cancelling).
- **Deferred, not a gap in this plan**: end-to-end "manager builds a template, generates a week" flow needs the client hook + UI from `/plan-design-review` before it's testable — this plan's server-side surface is independently testable via the routes above without it.

## Success Criteria

Qualitative: a manager can generate a full week of Draft shifts matching their venue's standard weekly pattern without recreating any shift by hand — informed by (not yet validated against) watching a real chef's actual behavior (see Assignment below); a post-ship observation pass should confirm this once built, not just this analysis.

Testable, for this repo's regression protocol: generating an 8-role week completes in a single API call, produces exactly N Draft shifts for N non-conflicting template rows with zero duplicates, and correctly skips (with an accurate skipped-count) any slot where a shift already exists.

## NOT in scope

- **Default assignee per template slot.** Deliberately rejected, not deferred by oversight — availability and compliance status change week to week, so baking in a default assignee risks generating a shift against someone no longer eligible. Assignment stays a manual step after generation.
- **A full recurring-event engine (Approach C).** Per-occurrence edit semantics ("this shift vs. all future ones") are a well-known bug-prone surface (DST, partial edits, series divergence) for a payoff the blueprint+generate model already covers.
- **A new "Templates" sub-tab.** Considered and rejected by `/plan-design-review` (2026-09-07) — resolved inline on the Calendar tab instead, see "UI Placement" above.
- **Watching a real chef build a roster before locking this architecture.** Raised by outside-voice review as a sequencing concern; explicit user decision was to proceed with the architecture lock now (pre-product, low cost of being wrong) and treat the observation as validation during/after implementation, not a gate before design.

- `assignStaff`/`claimSwap`'s `23505`-catch race-closing pattern — the precedent for the concurrent-generation unique-constraint fix.
- `roster:manage` permission — no new permission key, reused as-is for all six template routes.
